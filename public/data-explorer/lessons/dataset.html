Getting to know your data

Lesson 2 of 5 · about 15 minutes

What this lesson is for

In the first lesson you learned to press Run and read the answer. Now you will start asking questions of your data. Which district landed the most fish? How much was landed last month?

First, though, it helps to know how your data is arranged:

  • What does one line in the table stand for?
  • How do the lines fit together?
  • What is each column telling you?

That is all this lesson does. Once the shape of the data is clear, the next lessons will make sense. Go slowly, press Run on each box, and remember: you cannot break anything.

Where your data comes from

Your data does not appear from nowhere. Every time an enumerator meets a fisher coming back to a landing site, they fill in a short survey. It records the date, the landing site, the boat and gear used, how many people fished, and what was caught.

All of those surveys, from every landing site, are collected into one big table. That table is your data. Reading it is simply reading those survey records, stacked one on top of another.

A table has two simple parts:

  • a row is one line going across. One row is one record.
  • a column is one heading going down. One column is one piece of information that was recorded, like the date or the weight.

The rest of this lesson is about what the rows and columns in your table mean.

What one row means

Look at the very first line. It is one catch: species 1, 12 kg. The second line is another catch: species 2, 5 kg.

Each row is one catch — one kind of fish from one trip.

This is the first thing to hold on to. A row is not a whole trip, and it is not one fisher. It is one kind of fish that was recorded. So if a single trip brought back three kinds of fish, that trip fills three rows.

How the rows fit into trips

You may have noticed something that confuses almost everyone at first. The same district, the same date and the same trip_id appear on several lines.

Nothing is wrong. This is exactly how the data is meant to look.

The reason is simple. One fishing trip usually brings back more than one kind of fish.

Each trip is given an identity code, called trip_id. Every kind of fish from that trip gets its own row, and they all carry the same trip_id. That shared code is how you know which rows belong to the same trip. (survey_id works the same way. It names the survey the record came from.)

In the example, trip_1 brought back three kinds of fish, so it fills three rows. trip_2 brought back two, so it fills two rows. Here is that first trip drawn as a picture:

One trip, three kinds of fish → three rows, all sharing trip_id = trip_1.

The column n_catch writes that number down for you: it is how many kinds of catch the trip recorded. You don’t have to take it on trust — you can count the rows for each trip yourself. Press Run:

The result shows trip_1 3 and trip_2 2. Three rows for the first trip, two for the second. That matches the n_catch column exactly.

Counting how often something appears is already a useful skill, and you will use it again later.

Two kinds of columns

Now look across the columns. Once you see it, you cannot un-see it: the columns fall into two groups. (Here the colours mark the two kinds of columns — not the trips as before.)

About the trip (same on every row)
landing_date, gaul_2_name, gear, n_fishers, tot_catch_kg …
About each catch (changes on each row)
catch_taxon, catch_kg, length_cm, catch_price

Some columns describe the whole trip. The trip happened once, so these are the same on every row of that trip. They include landing_date, gaul_2_name, gear, and tot_catch_kg, the total weight the trip brought in.

Other columns describe each catch on its own, so they change from row to row. They include catch_taxon and catch_kg, the weight of that one kind of fish.

This difference matters in real work.

  • tot_catch_kg is the whole trip’s weight.
  • catch_kg is one kind of fish’s weight.

If you added up tot_catch_kg over every row, you would count the same trip several times. The number would come out far too big. So use tot_catch_kg for a trip total, and catch_kg for a single catch.

You do not need to memorise the columns. The next lessons introduce them one at a time. For now, just hold three things in your head:

  • A row is one catch.
  • Rows group into trips.
  • Every column is either about the trip or about the catch.

Looking at your own data

You now know the shape. Now look at your real landing records in the same kind of table. They were fetched for you when this page opened:

landings_state = {
  landings_reload;

  yield ({ phase: "loading" });

  const token = localStorage.getItem("authToken");
  if (!token) {
    yield ({ phase: "signed-out" });
    return;
  }

  const apiBase = localStorage.getItem("apiBaseUrl") || "/api";
  try {
    const res = await fetch(`${apiBase}/data-download/explorer-data`, {
      headers: { Authorization: `Bearer ${token}`, Accept: "application/json" }
    });
    if (!res.ok) {
      if (res.status === 401) {
        yield ({ phase: "signed-out" });
        return;
      }
      // 400/403 mean the account cannot reach this data (no forms assigned, district not
      // permitted). Showing "connection problem" there sends the learner hunting a fault that
      // does not exist, so the server's own sentence is passed through instead.
      if (res.status === 400 || res.status === 403) {
        let message = "";
        try { message = (await res.json()).error || ""; } catch { /* body was not JSON */ }
        yield ({ phase: "no-access", message });
        return;
      }
      yield ({ phase: "failed" });
      return;
    }
    // The endpoint returns a bare array. Normalising anyway: `rows.length` is read straight into the
    // panel text, so anything else here would throw and take the whole panel down with it.
    const rows = await res.json();
    const safeRows = Array.isArray(rows) ? rows : [];
    // Absent on an older deployment; the panel then just omits the sentence about the cap.
    const cap = Number(res.headers.get("X-Row-Cap"));
    mutable landings_rows = safeRows;
    yield ({ phase: "ready", rows: safeRows, cap: Number.isFinite(cap) && cap > 0 ? cap : null });
  } catch {
    yield ({ phase: "failed" });
  }
}

Two things that look different in your real table

The column headings are the same as the small example, so what you practised will work here. But two of the values look different, and it is worth knowing why before you go on.

  • The fish is a code. In your real data catch_taxon holds a short code (for example SKJ, which means skipjack tuna), not a plain name. The scientific_name column gives its full name. In the small example we simply wrote species 1, species 2 and species 3, so that nothing you practised depended on knowing which fish is which.
  • gaul_2_name is the district, not the landing site. The odd name comes from an international list of areas. Your table records the district a record belongs to, not the individual beach or jetty.

What you have learned

You can now read the shape of your data:

  • a row is one catch — one kind of fish from one trip;
  • rows belong together when they share a trip_id, and n_catch says how many a trip had;
  • every column is either about the trip (the same on every row) or about each catch (different on each row);
  • your real data has this same shape — just much bigger.

That is the foundation. In the next lesson you will start to find the rows you need. For example, only the landings from your district, or only one month.
